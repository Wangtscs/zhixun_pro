## 1. 先读这一页

**智巡·管廊是面向城市地下综合管廊的巡检与应急处置系统。** 原始目标是在OpenHarmony原生终端上，将感知节点、现场巡检、管理派单和两个AI智能体连成业务闭环。首要场景是地下综合管廊，后续可扩展到变电站电缆夹层等封闭空间。

产品希望减少人员在高危环境中的无效暴露，提前发现气体/温升趋势，并让缺少经验的巡检员获得有依据、能执行的处置步骤。重点是监测、任务与处置的协作，不是独立聊天机器人。

**当前仓库是软件业务阶段**：Vue网页端＋Spring Boot后端＋数据库，已有人员权限、节点监测、规则告警、工单、巡检、审计与报表。硬件、华为IoT、MQTT、软总线、Agent和原生App均未完成接入。用户正在把项目交给其他人开发鸿蒙App，已有[后端对接文档](鸿蒙App后端对接文档.md)。

## 3. 为什么要做

原稿归纳的三个痛点（第2页）：

1. **高危人工巡检**：封闭空间、照明不足、可燃气体与电缆过热，使人工逐点抄表和夜间巡检存在暴露风险。
2. **多源数据割裂**：气体、温湿度、红外温度各自报警，难以结合趋势提前发现风险。
3. **应急处置依赖专家**：纸质手册和电话求助效率有限，新人难以快速获得明确步骤与复核依据。

原稿中的“早十五分钟知道风险”等表述是产品愿景，不是已经测得的提前预警能力。原稿明确要求：未经样机实测的统计、效果和量化指标不能写成结论。

## 4. 用户与职责

| 产品角色 | 使用端 | 核心需要 | 当前实现映射 |
| --- | --- | --- | --- |
| 现场巡检员 | 鸿蒙手机/平板规划 | 本人任务、负责区域读数、按步骤执行、照片与读数回填 | INSPECTOR；网页已有相应流程，原生App待开发 |
| 值班长 | 管理端/大屏/平板规划 | 区域态势、派单改派、期限和优先级、结果复核 | MANAGER；按授权区域工作 |
| 运维主管 | 管理报表规划 | 覆盖率、响应时长、重复故障、风险复盘 | 当前可用管理视图/报表，没有独立SUPERVISOR后端角色 |
| 系统管理员 | 当前软件中的管理角色 | 建账号、分权限与区域、维护基础资料 | ADMIN；当前服务器最高权限 |

**原稿与当前权限的差别**：原稿把值班长描述为最高管理权限；当前代码由ADMIN承担最高权限，MANAGER受区域约束。后续AI不能为了照搬企划书而自动取消现有权限隔离。角色菜单切换视图不会改变服务器身份。

巡检员“只读任务相关数据”应理解为读取范围受限，仍需要执行接单、上传和提交等授权操作，不能理解成完全禁止其写入业务反馈。

## 5. 核心场景和业务闭环

### 5.1 日常巡检

原稿规划：巡检员进入管廊 → 终端自动发现节点 → 地图展示健康热力块 → 点开节点看实时及24小时趋势 → 完成检查和记录。

当前可做：登录、区域/节点查询、历史曲线、巡检任务、手动选点、照片和结果提交。自动发现、软总线、NFC打卡和原生离线缓存未实现。

### 5.2 异常预警

原稿规划：将当前值、变化速率、历史基线和邻近点位温升结合，生成趋势预警卡片，而非等单个阈值被突破。

当前可做：阈值、持续异常、通信离线、恢复与人工确认。现有规则告警不等于趋势预测；前端健康度展示也不等于经过验证的综合风险模型。

### 5.3 应急处置

原稿规划：语音/文字提问 → 检索运维规程 → 给出带依据的步骤 → 转成待确认工单 → 值班长确认/派单 → 巡检员执行 → 管理复核。

当前可做：人工维护手册、告警转单、派发/改派、接单/开始、照片和读数反馈、复核/退回/取消、时间线和审计。AI问答、语音、RAG及AI自动建草稿未实现。

当前软件演示流程：

```text
管理员建巡检员并授权区域
  → 配置节点和规则
  → 模拟上报/人工联调数据入口
  → 规则告警
  → 创建待派发工单
  → 值班长单人/双人派发
  → 巡检员接单、开始、上传记录、提交复核
  → 值班长通过或退回
  → 审计、通知和统计
```

## 6. 原稿的四层架构与当前位置

| 层级 | 原稿规划（第3、5页） | 当前状态 |
| --- | --- | --- |
| 感知层 | Hi3861轻量系统节点；甲烷、温湿度、单点红外测温；可选烟感 | 没有真实节点联调结果；使用模拟数据及统一上报服务 |
| 连接层 | WiFi/MQTT＋分布式软总线发现与流转 | 未接通MQTT/软总线；华为IoT作为后续接入方向，尚未连接 |
| 应用层 | ArkTS/ArkUI、Stage、EntryAbility，一套工程按角色分流；RDB、通知、NFC | 当前为Vue网页；原生App、RDB离线缓存、NFC和分布式状态同步待开发 |
| 智能体层 | 外部大模型API、RAG知识库、受限工具调用 | 未接入；仅保留分析数据结构及业务接口 |

Spring Boot负责鉴权、区域权限、数据存储、告警、工单流转和审计；当前MySQL保存业务与监测历史，Flyway迁移到V9。不得因原稿写“时序数据”就推断已部署独立时序数据库。

原稿的“鸿蒙原生”特指OpenHarmony产品路线。用户现计划开发“鸿蒙App”，但具体OpenHarmony发行版/HarmonyOS SDK、设备、API级别尚需开发者确认；二者的API、软总线能力和设备支持不能自动视为相同。

## 7. 两个Agent的岗位定义（规划）

### 环境安全预警Agent

- 输入：当前读数、变化速率、同类点位历史基线，结合相关点位异常。
- 输出：风险等级、涉及节点、预计越阈时间、建议动作、判断依据。
- 价值：识别“提前”风险；无可靠证据时预计越阈时间可空，不编造精确预测。
- 当前不存在可调用的Agent接口，也没有实测准确率、误报率或提前时长。

### 应急抢修专家Agent

- 输入：现场语音或文字问题，以及有授权的节点/告警上下文。
- 知识：管廊/电力运维文档经过整理、切片和检索；回答带来源。
- 输出结构：判断依据 → 处置步骤 → 复核要点；原稿要求步骤不超过五步，每步为可执行动作。
- 当前的人工手册不是已完成的向量库或RAG问答。

### 权限与失败边界

原稿限定四类工具：查实时数据、查历史、建工单、派单。原稿同时写“AI只读不写业务库”，应区分：**模型不能直接写库；确需产生业务变更时通过有权限校验、审计和人工确认的业务服务**。当前预留契约建议先创建DRAFT草稿，由人确认，不让模型绕过现有派单权限。

原稿要求高危动作由确定性规则约束，模型只解释和排序。当前没有断电、撤离控制或封闭区段执行接口，不能把既有告警规则表解释成已经实现这些安全控制。后续控制规则及阈值需要领域验证。

模型超时、输出不合规时，原稿要求固定话术/标准步骤兜底。未来实现需清楚标注降级来源，不能生成虚假检索出处或假装已执行现场动作。

## 8. 地图与数据语义

- 原稿本期目标是2.5D俯视管线图和热力块，完整3D数字孪生明确延期；当前为二维管廊示意图，不能写成完整数字孪生已完成。
- 节点内部ID与code、外部设备编号external_id、位置area/section/corridor要区分；页面x/y坐标不是人员实时定位。
- 单位以现有后端契约为准：甲烷%LEL、湿度%RH、环境/红外温度°C；外部设备ppm等单位必须在适配器正确转换。
- 模拟数据、真实设备数据和AI结果应有来源区分。网页独立演示环境是内存数据，不代表后端持久化或App已有演示接口。
- 原稿提到“谁在什么位置”，但当前无工人定位/跟踪能力；不能用节点坐标或所属区域替代人员定位。

## 12. 后续开发建议与待定项

**建议顺序**：先让原生App调用现有后端跑通本人任务闭环，再独立完成真实设备适配，最后接Agent。这样每一层都有可单独验证的数据和失败边界，不把当前规则模拟误当作模型或硬件已完成。

在相关模块开发前，需要明确：

1. 原生工程目标：OpenHarmony还是具体HarmonyOS SDK，手机/平板型号、API级别、发行方式。
2. 设备最终路线：Hi3861验证结果、是否切ESP32、是否使用华为IoT、软总线具体参与哪段链路。
3. 数据身份：设备凭据/回调认证、外部ID映射、单位标定与重试去重；不能借用管理员JWT充当设备身份。
4. 健康度和风险卡片：计算口径、依据、对照数据、误报/漏报及越阈时间评估方法。
5. 知识库与Agent：规程来源/版本、模型提供方、结构化输出、超时降级、人工确认界面。
6. 离线策略：哪些数据可缓存、哪些动作可排队、服务端状态变化后如何冲突处理，不能默认离线建单天然幂等。
7. 主管/值班长角色差异、人员定位是否本期范围；现有ADMIN/MANAGER/INSPECTOR保持为代码事实。

开发现有接口先读[鸿蒙App后端对接文档](鸿蒙App后端对接文档.md)；新增硬件或Agent边界先读[integration-contracts.md](integration-contracts.md)。没有实测证据时，文档和演示统一写“规划/模拟/待验证”。
