# 鸿蒙 App 专用后端设计

鸿蒙 App 连接本仓库内独立开发和部署的移动服务；移动服务调用现有业务 API。网页前端、现有业务后端和数据库均保持原样。工单、巡检任务、点位结果和审计记录继续由现有后端统一管理；两端使用同一记录 ID，无需迁移或同步数据。

## 方案选择

- 已选：移动服务通过现有 API 读写数据。可以独立演进鸿蒙接口，同时保留现有权限、状态流转及审计。
- 双服务直接访问同一数据库：会绕过现有 API 的业务边界，需要重复实现权限和写入规则。
- 新后端接管共享业务：需要迁移网页端接口或替换现有后端，超出本次范围。

## 首版范围

1. 在本仓库新增独立的 `backend/` 服务。建议使用本机已安装的 Node.js 24，首版不新增运行时依赖或数据库。提供启动说明、独立监听端口和健康检查。
2. 保持鸿蒙端当前登录、节点、告警、工单、手册、个人资料和助手接口的请求与响应约定，通过明确的方法和路径清单转发。App 的服务地址和命名改指向鸿蒙后端；本地演示入口继续独立使用。
3. 新增原生「巡检任务」入口，读取本人任务、任务点位、既有结果和关联工单编号，支持填写检查结果并标记异常。通过移动服务接入现有 `GET /api/business/patrol/runs`、`GET /api/business/patrol/runs/{id}` 和 `POST /api/business/patrol/results/{id}`。提交成功后重新拉取任务详情；异常工单由上游在提交事务内创建。
4. 网页继续负责创建计划、生成巡检任务、派单和复核；首版不新增离线同步、照片上传或独立账号体系。

## 接口与故障处理

- 上游地址由服务环境配置，App 请求不能指定转发目的地。逐请求使用登录用户的 Bearer 凭证，由上游校验区域授权及角色。移动服务不存储密码或令牌，不记录敏感请求内容。
- 保留上游 HTTP 状态与业务响应；连接失败和超时返回可读的错误，不回退到示例数据。提交遇到超时不自动重试，先刷新任务详情核对结果。未确认成功前保留输入；若提交已确认但刷新失败，则分别提示提交成功和刷新失败。
- 生产环境通过 HTTPS 访问。健康检查区分移动服务进程存活和上游 API 可用；部署时使用单独的端口或域名。

## 验收

- 在隔离的测试环境准备管理者账号、同一区域的巡检员账号和测试点位。用网页生成并派发巡检任务；巡检员在鸿蒙端登录，打开同一个任务 ID，提交异常点位结果；网页刷新后能看到同一个巡检结果 ID 和同一个关联工单 ID。没有可用测试环境时，单独标记双端联调尚未验证。
- 在网页派发该工单，鸿蒙端接单、开始处理并提交复核；网页刷新可复核同一工单，鸿蒙再次读取可见最新状态。
- 验证未分配的巡检员不能提交结果，重复提交不产生额外工单，上游不可用时 App 不显示成功。自动化测试覆盖接口边界和故障处理，另用真实上游和模拟器完成双端闭环。
